# 架构：谁做什么，怎么连接

> 状态：草案，待产品负责人确认。遵守 `00-product.md` §5.1（AI 管判断，代码管保证）、§5.2、§5.9。
> 本文回答：系统里有哪几类角色，各自的边界是什么，它们怎么耦合，怎样避免无限膨胀。
> **不回答**：具体流程（见 `modules/`）、数据格式（见 `contracts/`）、实现语言、库和代码目录（见 `design/`）。

## 1. 五类角色

```
        数据表 ──(只读)──┐
                         ▼
 原件 ─→ [Tool 读取] ─→ 视图 ─→ [Harness] ⇄ [Agent]
                                  │ 校验 / 路由 / 重试 / 降级
                                  ▼
                           [Tool 编辑·比对] ─→ 产物
 外壳：任务目录、只读输入、权限、预算、发布、界面
```

| 角色 | 它是什么 | 可以做 | 不可以做 |
|---|---|---|---|
| **Agent** | 语义判断者（AI） | 在 Harness 给的有边界的视图上做判断；输出引用 `source_id` 的结构化结论 | 读写文件；调用文档工具；决定处理方式；说出格式数值；自造 id；决定是否重试 |
| **Harness** | 裁判兼调度员（代码） | 构造给 Agent 的视图；按数据表路由；校验输出（完整、唯一、在词表内）；把具体错误反馈给 Agent；重试；降级到安全下限；记录 | 做语义判断；直接改 Word；为修补个例随意加规则 |
| **Tool** | 确定性的 Word 能力（代码） | 读取对象、度量生效格式、执行编辑原语（保留 / 删字 / 换占位 / 克隆结构）、渲染、对原件做差异比对 | 知道流程；做决定；保存跨调用的状态 |
| **数据表** | 随产品演进的配置（数据） | 单元类型及处理方式、骨架、字段注册表、预设样式、提示词模块 | 含逻辑；被执行 |
| **外壳** | 任务边界（代码） | 任务目录、只读输入、权限、预算、最终发布、界面提示 | 参与任何文档判断 |

**Agent 的默认形态**：干净的上下文，一次进、一次出。Harness 把它需要的内容放进输入，它返回结构化结果。收到 Harness 的反馈后，它可以修正；这一轮是否允许它调用只读的检查工具，由实验决定，不预先设定。实验顺序（选满足质量线的最简单一档）：

| 档 | 做法 |
|---|---|
| E1 | 一次进、一次出，看质量 |
| E2 | 出错后 Harness 只用文字反馈，不给工具，Agent 基于反馈修正 |
| E3 | 出错后 Harness 反馈，并允许 Agent 调用只读检查工具核查 |

**Harness 与 Claude Agent SDK 的关系**：Harness 是我们基于 SDK 实现的一个很薄的循环。SDK 提供 Agent 运行时；Harness 只补 SDK 没有的、本项目定制的检测与调度。已验证（`spikes/sdk-check/README.md`）：

| 事情 | 谁做 |
|---|---|
| 输出格式合法（JSON schema、枚举） | SDK（`output_format`） |
| 同一会话追加反馈 | SDK（`ClaudeSDKClient`） |
| 零工具、干净上下文 | SDK 配置：`tools=[]`、`setting_sources=[]`、`disable-slash-commands`、关闭自动记忆 |
| 完整、唯一、词表内、路由、降级、重试次数 | **Harness（自写）** |

循环形态：`query()` → 取结构化输出 → Harness 校验 → 不通过则在同一会话用 `client.query(具体反馈)` 追加 → 通过则继续。不依赖 `Stop` 钩子。

## 2. 耦合规则

依赖方向是单向的：

```
外壳 → Harness → Agent
          ↓
        Tool
          ↑
       数据表（被 Harness 和 Tool 读取）
```

1. Agent 不直接接触 Tool。
2. Tool 不知道 Harness 和 Agent 的存在。
3. Harness 不含 Word 内部细节；对文档的任何操作都经过 Tool 的接口。
4. 数据表只被读取，改变行为时**优先改数据，不改逻辑**。
5. 模块 A、B、C 之间只通过产物（合同）交接，不引用彼此的代码和内部状态。

## 3. "遇到这件事谁管"

| 事情 | 谁管 |
|---|---|
| 这块内容是不是封面 | Agent（认） |
| 封面该怎么处理 | 数据表 + Harness（查表） |
| 每个对象是否都被分到了一个单元 | Harness |
| 对象的生效格式是什么 | Tool |
| 同一角色下多个示例格式冲突时选哪个 | Harness 按固定规则，Tool 提供指纹 |
| 删掉文字后有没有动到别的 | Tool 比对，Harness 判定 |
| 重试几次、何时放弃并退回安全下限 | Harness |
| 新增一个单元类型 | 数据表 |
| 结果写到哪里、能不能覆盖 | 外壳 |

## 4. 防止膨胀

这是本项目最重要的工程约束，旧项目一个文件长到 5000 行，教训见 `03-lessons.md` P01、P03。

**代码**
1. 每个文件只承担一个角色的一件事。文件超过约 400 行，必须拆分；超过前先说明为什么不能拆。（数字待产品负责人确认）
2. 不设"总管"文件。流程由 Harness 的小步骤串起，每步可单独运行和重放。
3. 新增任何机制、检查、特例之前，先回答：它属于哪个角色？它防的是哪条不变量？回答不了就不加。
4. Harness 的检查数量有上限，登记在一处；新增检查要替换或合并，而不是叠加。
5. 能用数据表解决的，不写进代码。
6. 用自动检查守住边界：文件行数、依赖方向（Tool 不得引用 Harness 等），在提交前运行。

**产物**
7. 每步产物落盘，格式固定（`contracts/`），可单独检查和重放。

文档的体量约束见 `README.md`。
