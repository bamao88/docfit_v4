# 文档地图与规则

> 本文回答：有哪些文档，该先读哪份，新内容写在哪里，怎样避免文档膨胀。

## 阅读顺序

1. `00-product.md`：产品是什么、模块边界、怎么耦合、横向原则。**所有工作之前先读。**
2. `02-architecture.md`：Agent / Harness / Tool / 数据表 / 外壳的边界。
3. 你要做的模块：`modules/` 里的对应文档，以及它引用的 `contracts/`。
4. 写代码之前：`design/`（代码怎样组织，每个文件负责什么）。
5. `01-acceptance.md`：做到什么程度才算对。
6. 想知道先做什么、当前阶段的范围：`05-roadmap.md`。
7. 遇到问题或不确定时：`03-lessons.md`（旧项目教训）、`04-decisions.md`（已决定与待决定）。

## 目录

```
00-product.md       产品层：是什么、边界、耦合、原则
01-acceptance.md    端到端验收与黄金标准
02-architecture.md  角色边界与防膨胀规则
03-lessons.md       问题档案（只增不删）
04-decisions.md     决策记录（已决定 / 待决定）
05-roadmap.md       开发阶段与每阶段的完成条件
status.md           当前做到哪了、下一步做什么
modules/            各模块的流程、风险、验收
contracts/          模块之间的交接物格式
design/             系统设计：代码目录、文件职责、Tool、Harness、数据与运行目录、旧项目复用
```

## 规则

1. **一份文档一个目的。** 开头写明"本文回答什么、不回答什么"。写着写着超出范围，就另开一份。
2. **每个事实只写一处。** 其他地方用链接引用，不复述。复述必然过期。
3. **体量预算。** 顶层文档（00–04）每份不超过约 200 行；modules、contracts 每份约 150 行。接近上限时拆分，而不是继续追加。（数字待产品负责人确认）
4. **按文档的性质放置：**
   - 决定了什么 → `04-decisions.md`
   - 出过什么问题 → `03-lessons.md`
   - 做到什么程度才算对 → `01-acceptance.md`
   - 流程、风险 → `modules/`
   - 交接物格式 → `contracts/`
   - 代码怎样组织、每个文件负责什么 → `design/`
   - 按什么顺序做 → `05-roadmap.md`
   - 当前做到哪了 → `status.md`；状态必须写明验证等级和适用样本
5. **下层不得改变上层的结论。** 上层的改动由产品负责人确认。冲突时停下并指出。
6. **过期就删除或明确标注。** 已完成的计划、被推翻的设计，不留在当前目录里当作事实。
7. **本文自身也受这些规则约束。**
