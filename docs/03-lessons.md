# 已知问题档案

> 旧项目约两个月的教训。每条：发生了什么、根因在哪一层、对上层提出了什么约束。
> 遵守 `00-product.md`。只增不删：新问题追加，已解决的标注解决方式。编号 P 开头，被其他文档引用，不要重新编号。


### 架构与方法类

**P01 · 架构摇摆，两套模型叠在一起**
- 现象：先定"一个主 Agent 掌握全局"，后来因为效果不好，又逐步加出分单元、分批、检查点、门禁。最终是单 Agent 架构上叠了流水线，`prepare_template.py` 达 5000+ 行，全项目约 6 万行。
- 根因：没有先定清楚"谁判断、谁保证"，出问题就在最近的地方加一层。
- 约束：架构一旦定下，修复必须在对应责任层，不允许叠加第二套调度机制。

**P02 · AI 被当成转写器**
- 现象：一次真实运行里，所有返工都是协议错误——数空格、把制表符写成字面字符、字段与角色组合不合法。没有一次是学校语义判断错。86% 的时间花在思考上，输出本身只有几 KB。
- 根因：要求 AI 在判断语义的同时，输出精确的字符数、偏移和转义。
- 约束：AI 的输出只引用 `source_id` 和可见文字；字符层面的对齐由代码完成。

**P03 · Harness 与门禁增殖**
- 现象：为了防止某类错误，不断添加新检查；检查本身又需要被修复。门禁主要在考 AI 是否遵守传输格式。
- 约束：见 00-product.md §5.2。新增任何检查前，必须说明它属于哪个层、防的是哪个不变量。

**P04 · 个例被固化成流程**
- 现象：把某次模型的失误，写成应用里的专门分支、专门提示词。
- 约束：先判断是领域指引不足、执行能力缺口还是验收缺口，再决定改哪里。不能用提示词弥补执行层的缺陷。

**P05 · 调度：串行、整批重交**
- 现象：17 批串行共用约 1 小时预算；任何一处错误，整批重新提交；一个长尾拖垮整份模板。
- 约束：一个对象合格就立即接受，只重发出错的；天然独立的单元可以并行。

### 对象与身份类

**P06 · 身份漂移**
- 现象：拆分对象后 ID 变化；Tool 靠全文搜索另选对象；"某段文字"在目录和正文各出现一次时指错对象。为此做过一次专门的"全流程对象身份"工程。
- 约束：见 00-product.md §4.5。

**P07 · 逻辑单元 ≠ 物理分页**
- 现象：把封面末尾的空段和声明页开头的空段当成一样的东西，拆分后声明标题多下移一行；按页切分后反推结构；示例章节被当成多种模板能力；页眉页脚、脚注等"附属内容"和正文混在同一个单元里（真实 NJAU 回放因此失败）。
- 约束：先按内容职责定逻辑单元，再分析分页怎样承载它。分页边界只能有一个所有者。附属内容与正文分开归属。

**P08 · 空对象的噪声**
- 现象：模板里约 1/3 的对象是空段落，被逐条要求判断并写理由，既浪费注意力又引入错误。但空段落也可能承担语义（留白、签名区、分页载体），不能一概默认保留。
- 约束：对空对象紧凑展示、允许批量，但保留逐个覆盖的能力。

### 语义类

**P09 · 删除说明文字时丢了规则**
- 现象：模板里写着"目录标题前空三行""参考文献另页开始""仅实名评审时填写"，直接删掉文字后，这些规则就消失了。
- 约束：每个"删除"决定，如果被删文字带有规则，必须先有新的承载位置（样式、分页、条件、人工区）。
- 2026-10-08 修订（待确认）：多数规则在原件里已经体现（如"空一行"本来就是真实的空段落）。以原件实际格式为准，只上报"说明与原件不一致"的差异，不自动迁移。同时，复杂单元类型直接"原样保留"（见 00-product.md §4.7），从根上减少需要迁移的场合。

**P10 · 靠表面特征判断内容角色**
- 现象：红字就删、方括号就当占位符、空白格就当槽位、整页声明都设成可填写。
- 约束：先判断内容角色（固定、填写、生成、人工、说明、条件、不明），表面特征只是线索。

**P11 · 概念边界模糊导致反复摇摆**
- 现象：对"占位符 + 格式括注"、"正文代表结构"这类内容，反复在填写/保留/清理间摇摆，因为各类别"产出什么"没讲清。
- 约束：保留 / 填写 / 删除三种语义的产物含义，必须在本层之下的合同里一次性讲清，Prompt 不能代替合同。

### 执行与格式类

**P12 · 执行不忠实于判断**
- 现象：AI 判断的是"一句话里的这半句"，执行时却以整段、整个控件为单位操作；执行器自报"已保留"但实际没有；图片清理删掉了所在整段。
- 约束：执行必须以判断时的最小范围为准；完成后重读产物，与原始对象清单逐项比较，回执由差异生成，不由执行器自报。

**P13 · 复合对象只改了看得见的部分**
- 现象：目录（域、标题层级、样式、缓存）、自动编号、参考文献链接、图表题注、页码、内容控件，只处理了可见文字；参考文献的编号根本不在文字里，替换段落属性时被悄悄删了。
- 约束：识别复合对象的完整关系，修改和验证都覆盖整个关系。

**P14 · 样式名 ≠ 实际格式**
- 现象：样式名正确但被直接格式覆盖；"假居中"（居中属性在，缩进让视觉偏移）；旧目录缓存抵消了错误样式，重建后才暴露。
- 约束：面向最终生效的格式判断和验证，不面向样式名。

**P15 · 兜底样式与学校样式混用**
- 约束：见 00-product.md §3.4。一个角色整体来自学校或整体来自预设。

### 验证与状态类

**P16 · 验证层次混淆**
- 现象：包能打开 ≠ 内容完整 ≠ 行为正确 ≠ 版式正确。同一模板在 LibreOffice 里 15 页、在 Word 里 17 页。
- 约束：见 00-product.md §5.6。

**P17 · 完成度被说高**
- 现象：状态文档里"已通过"只是单元测试层或特定样本层，被当作整体能力；计划文档、过期状态被后来的 AI 当成事实读取。
- 约束：见 00-product.md §5.5。每份状态必须写明验证等级和适用样本。

**P18 · 模块边界被联调污染**
- 现象：为了尽快看到最终效果，把学生内容提取和模板提取放在一起调；Gold 互相印证；一个模块的修复依赖另一个模块的私有状态。
- 约束：A、B 独立。端到端验证单独设一层，不借用模块内验证的结论。

**P19 · 上下文污染**
- 现象：产品 Agent 运行时，加载了开发仓库的规则文件和无关的 CLI 技能，进入了产品上下文。
- 约束：产品 Agent 的运行环境与开发环境隔离，只带它需要的材料。

**P20 · 缺失处理没有产品策略**
- 现象：必填缺失、非必填缺失、不适用、无可靠来源，在不同模块被各自处理。
- 约束：见 00-product.md §4.1，只在 C 里统一处理，并写入交付报告。

**P21 · 文档体量失控**
- 现象：状态、计划、讨论、证据混在同一层，AI 每次启动要读大量过期内容，而真正的"当前真相"反而难找。
- 约束：文档分层（见 README.md）。上层短且稳；细节、证据放下层，且不能反过来定义上层。
