## 1. 设计原则

1. **设计一次做全，实现按阶段做薄。** 所有包、步骤、产物、交接格式的位置现在就定下来。S0 只实现其中一部分，后续阶段是"往空位里填"，不是"改结构"。
2. **阶段范围由数据裁剪，不由代码裁剪。** "S0 只有正文是填写单元""S0 只处理标题和段落"写在数据表里（单元类型表、角色表），代码对所有类型一视同仁。加宽一个阶段 = 改数据 + 加处理函数。
3. **一切通过落盘的产物交接。** 每个步骤是"读若干文件 → 写若干文件"的函数，同输入同输出；AI 步骤靠调用缓存做到可重放（`03-harness-agent.md` §6）。
4. **验证不信任执行者。** 执行步骤之外，由纯函数推导"预期产物"，再独立读取"实际产物"，两者比对（`02-tool.md` §5）。
5. **旧项目默认不复用。** 只有通过 `05-reuse.md` 准入条件的才拿；数据类只拿已验收的取值。
6. **模块对称。** A 和 B 都是"读取 → 划分区域（AI）→ 检查 → 区域内判定（AI）→ 检查 → 产出"。它们共用 Tool 和 Harness 的通用部分，但各自的步骤脚本、数据和产物互不引用。

## 2. 系统总图

```
                     shell：CLI、任务目录、资产库、发布
                                   │
     ┌─────────────────────────────┼──────────────────────────────┐
     │ pipelines/a_template   pipelines/b_content   pipelines/c_assemble │  每个模块一组步骤脚本
     └──────────┬─────────────────────────────────────┬──────────┘
                │                                     │
     harness：判定循环、校验器、视图、提示词组装        tool：读取、生效格式、编辑原语、比对、渲染
                │                                     │
     agent：模型调用适配、缓存                          │
                └─────────────── core：id、产物读写、schema、数据表加载 ───┘

   data/ 数据表      assets/ 模板资产库      runs/ 任务目录      eval/ 评测（运行时不依赖）      checks/ 架构守卫
```

角色对应（`02-architecture.md` §1）：

| 角色 | 代码位置 |
|---|---|
| Agent | 不是代码；由 `agent/` 调用，提示词在 `data/prompts/` |
| Harness | 通用部分在 `harness/`；各模块的步骤编排在 `pipelines/` |
| Tool | `tool/` |
| 数据表 | `data/`，由 `core/datatables.py` 读取 |
| 外壳 | `shell/` |

## 3. 三个扩展方向的扩展点

| 扩展 | 改什么 | 不改什么 |
|---|---|---|
| 新内容角色（S1：图、表、公式、题注） | `data/registry/roles.yaml` 启用角色；B 的提示词；C 加 `fill/handlers/<角色>.py`；若需要新的 Word 操作，`tool/edit/` 加一个原语文件 | 步骤顺序、Harness、交接格式结构 |
| 新填写单元（S2：摘要、参考文献、致谢） | `data/unit-types.yaml` 改一行；`data/skeletons/<类型>.yaml`；`data/prompts/a/judge-unit/<类型>.md`；B 的区域表同理 | 代码 |
| 新学校（S3、S4） | 无代码改动：对新模板跑 A，人审入库 | 一切代码 |
| 换模型或调用底座（Q12） | `agent/backends/` 加一个后端 | Harness 及以上 |
| 新校验 | 在 `harness/validators.py` 的登记表里替换或合并一项 | 登记表总数不增加 |

如果某个阶段的扩展需要改"不改什么"那一栏，说明设计有问题，先回到本文修正，再写代码。

## 4. S0 的裁剪

S0 实现**所有步骤脚本**，让 A → B → C 整条链存在；薄的地方全部由数据和处理函数的多少决定：

| 内容 | S0 | 后续 |
|---|---|---|
| A 的十个步骤 | 全部实现 | 不变 |
| 填写单元类型 | 数据中只有"正文" | S2 改数据 |
| B 的区域判定 | 全部区域类型都识别 | 不变 |
| B 的区域内判定 | 数据中只对"正文"运行 | S2 改数据 |
| 内容角色 | 标题（各级）、段落、暂不支持 | S1 启用图、表、公式、题注 |
| C 的处理函数 | 标题、段落 | S1、S2 逐个增加 |
| 目录 | 南农为真实目录域，原样保留 | S4 的手打目录用 `tool/edit/toc.py`（预留位置，S0 不写） |
| 页眉页脚 | 读取并归属，不判定 | S3 |
| Agent 档位 | E1 | Q7 实验后决定 |
| 渲染 | LibreOffice 辅助；Word 人工打开 | 视需要接入 Word 自动化 |

## 5. 技术选型（待确认）

| 选择 | 理由 |
|---|---|
| Python 3.12、uv、ruff、mypy、pytest | 与旧项目和 SDK spike 一致 |
| **lxml 写 OOXML**，自写很薄的包读写层 | 不用 python-docx：它不覆盖内容控件、域、编号，往返保真度不够。写入不用标准库 ElementTree：它会改写命名空间前缀，旧项目为此专门打了补丁。只读的旧模块（如生效格式解析）照常使用 ElementTree，不必改 |
| pydantic v2 定义交接物 | 一份定义同时用于产物校验和 Agent 的 `output_format` schema |
| YAML 写数据表，JSON 写产物 | 数据表给人改，产物给代码读 |
| import-linter 守依赖方向 | `02-architecture.md` §4.6 |
| LibreOffice 渲染作辅助，Word 实机作最终裁决 | `01-acceptance.md` §7 |
