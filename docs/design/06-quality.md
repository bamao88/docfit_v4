# 结果验证体系：Checks、Tracing、Evals、Review

> 状态：草案。遵守 `00-product.md` §5.5–5.7、§5.10；执行与监督流程见 `06-workflow.md`。
> 本文回答：为什么这样设计自查、它由哪些部分组成、报告里有什么。
> **不回答**：具体怎么运行——那是 Skill `.claude/skills/docfit-evals/SKILL.md` 的事。本文只讲"为什么"和"是什么"，Skill 讲"怎么做"。

## 1. 来自旧项目的教训

旧项目在这上面投入了将近 2 万行代码，结果反过来拖累开发：**它在审计 AI 的过程，而不是检验产品的结果。**

| 旧问题 | 证据（旧项目路径） |
|---|---|
| 检查"有没有加载规定技能""有没有逐页看完" | `src/docfit/app/convert.py` 的后置检查 |
| 检查器写错，AI 退回更差的版本绕开它 | `docs/bugs/docfit-template-paragraph-cleanup-descendant-verification.md` |
| 评分代码 1.2 万行，真值始终是"候选" | `evals/template-extraction/cases/*/case.yaml` |
| 真值从 AI 输出晋升而来，评测中途升级注册表 | `docs/status/active/docfit-student-content-dependencies-and-blockers.md` |
| 观测 7600 行，没有使用者 | `docs/status/active/docfit-o0-local-observability.md` |
| 一次 188/188 就标"通过"，重跑只有 178/188 | 学生内容评测状态 |

## 2. 七条约束

1. **只检查结果，从不检查过程。** 每项检查写明守哪条产品不变量、属于哪一层。
2. **检查器自己要被测试。** 每项检查配正反样本；失败时先判断是产品错还是检查器错。
3. **先有真值，再建评分。** 没有产品负责人认可的黄金标准，就不写对应的评分代码。
4. **真值独立、冻结。** 原件上的人工批注，不从 AI 输出晋升，修改需批准。
5. **观测必须有使用者。** 运行轨迹的使用者是全链路视图和链路分析（`contracts/run-trace.md`），不为观测而观测。
6. **一次成功不算数。** AI 步骤重复运行并报告一致率。
7. **快、离线。** 重放用缓存，不调用模型；只渲染变化的页。

## 3. 为什么用 Skill 承载

- 验证是一套**会演进的操作**：脚本、标准文件、提示词、HTML 模板要一起维护。写成文档只能靠 AI 读懂后照做；写成 Skill，开发代理一调用就是同一套固定动作。
- Skill 与产品代码物理分开：产品运行时不依赖它（`00-product.md` §5.7）。
- `CLAUDE.md` 规定每件任务收尾必须调用它；没有报告的任务不算完成。

## 4. 四个部分与边界（D22）

| 部分 | 回答的问题 | 范围 | 需要标准答案 | 用 AI | 在哪 | 上线后 |
|---|---|---|---|---|---|---|
| **Checks** | **这一次运行**的产物有没有违反不变量？能不能往下走、能不能交付？ | 一次运行 | 否 | 否 | 业务代码：A⑨、B⑧、C⑤ | 在 |
| **Tracing** | 产品 AI 每一步看到、想到、说了什么，被怎样纠正？ | 一次运行 | 否 | 否 | 业务代码：运行时记录（`contracts/run-trace.md`） | 在（本地） |
| **Evals** | **产品的能力**怎么样：对不对、比基线好坏、稳不稳、错在哪层？ | 全部冻结样本 | 是 | 链路分析用 | Skill `docfit-evals` | 不在 |
| **Review** | **这件开发任务**能不能接受？ | 一件任务 | — | 审计用 | 流程（`06-workflow.md` §6–7） | 不在 |

### 为什么保留 Checks

看起来 Checks 和 Evals 都在"检查"，但它们服务的对象不同，不能互相替代：

- **Checks 是产品自己的安全保证。** 用户转换论文时，面对的往往是没有标准答案的新学校，Evals 根本无法运行；这时唯一能拦住"丢了学生内容""Word 打不开"的，就是 Checks（`00-product.md` §5.1"代码管保证"、§4.4）。取消 Checks，产品上线后就没有任何质量门。
- **Evals 衡量能力，不做把关。** 它回答"这版产品在样本上做得怎么样"，结论是分数和趋势，不决定某一次用户转换能否交付。
- **重叠只在于"内容守恒"这类事实**，处理方式是：**Checks 计算，Evals 只读取汇总**，不重新实现。这样一条不变量只有一份代码。

### Checks 的范围

- **只检查步骤产物的不变量**：内容守恒（不丢、不改、不重）、模板在授权范围外不变、格式等于选定原型、复合对象完整、文件可重新打开。登记在一处，不超过 8 项（`02-architecture.md` §4.4）。
- **不做**：不对比标准答案（那是 Evals）；不对比上一次运行（那是 Evals 的基线）；不打质量分；不调用 AI；不判断语义对错，例如"单元划分对不对"（那是 Evals 的黄金对比）。
- **也不是 Validators**：Validators 在判定循环里检查产品 AI 一次输出的合法性并触发重试（`design/03-harness-agent.md` §2）；Checks 在步骤出口检查产物。
- **失败时**：开发期，记入 Tracing 并在 Evals 报告里标红；用户转换时怎么处理，待 Q17。

### 谁能改什么

| 东西 | 谁能改 |
|---|---|
| Checks、Tracing 的代码 | AI，随产品改 |
| Checks 清单 | AI 提议，产品负责人批准 |
| Evals 的 `standards/`（冻结样本、黄金标准、阈值） | **只有产品负责人** |
| Evals 的 `scripts/`、`prompts/analyst.md` | AI；与产品修改分开提交，正反样本必须通过 |
| Review 的审计提示词 `prompts/auditor.md` | **只有产品负责人** |
| 基线 `runs/baseline/` | 只在产品负责人接受任务后更新 |

### 三个 AI 角色

| 角色 | 做什么 | 上下文 |
|---|---|---|
| 开发代理 | 做任务，调用 Skill | 完整开发上下文 |
| 分析代理 | 沿链路找第一个出错的地方，把错误聚类、归层 | 新会话，只读，只拿运行数据 |
| 审计代理 | 核对报告里每一句说法有没有证据 | 新会话，只读，只拿报告和任务卡 |

## 5. HTML 报告

单文件、无外部依赖、只留在本地（含学生论文内容）。数据先写成 `report.json`，HTML 由它生成：人看 HTML，审计代理读 JSON，看到的是同一份事实。

| 页签 | 内容 |
|---|---|
| **总览** | 任务卡、审计结论、记分板与基线对比、红灯、未验证项、需要决定的事 |
| **变化对照** | 每个变化页三栏：原件 / 基线 / 本次；范围外变化标红 |
| **全链路** | 每个样本一条流程图（A、B、C 各步骤），节点颜色表示正常 / 降级 / 未决 / 失败，标出第一个出错的步骤。点进一步，看到每个对象：产品 AI 看到的视图 → 它的思考 → 它的输出 → 校验错误与重试 → 最终结论 → 黄金标准 |
| **链路分析** | 分析代理的结论：第一个出错的步骤、错误聚类（每类引用对象，点击跳到全链路）、原因属于哪一层、没能确定的地方 |

**事实与推断用颜色区分**：记分板、差异、轨迹是机器事实；链路分析是 AI 推断；审计结论单独一栏。产品负责人一眼能分清哪些是数据、哪些是 AI 的看法。

## 6. 什么能拦住工作

只有两类：不变量失败、冻结样本回归失败。性能微基准、字段集合的严格断言、过程合规类检查，一律不拦。
